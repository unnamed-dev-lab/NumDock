# NumDock 后端 Agent 开发规范

本文件适用于 `backend/` 及其子目录，与根目录 `AGENTS.md` 一起遵守。原始工程提示词完整保存在 `ENGINEERING_PROMPT.md`；本文将其整理为后端执行约束。前端实现和视觉规范由 `../frontend/AGENTS.md` 负责。

## 1. 架构与技术栈

- 使用已验证的稳定 Go 版本、Chi、pgx + sqlc、PostgreSQL、River、Redis、slog、OpenTelemetry、OpenAPI、SSE 和 Docker。实施时核实官方文档与版本兼容性，不在文档中猜测最新版本。
- 优先 Go 标准库，按真实需求增加依赖；保持强类型，避免无意义的 `any`、类型断言和无收益抽象。
- 首先采用按领域组织的模块化单体，不提前拆分微服务。后端负责全部核心业务、权限、金额计算和状态转换。
- Go module、API、worker、数据库迁移、SQL 查询和 OpenAPI 契约均归入 `backend/`，不再沿用原稿中仓库根目录的 `apps/api` 方案。
- 推荐按实际需要建立 `cmd/api/`、`cmd/worker/`、`internal/<domain>/`、`internal/platform/`、`db/migrations/`、`openapi/`。每个领域拥有自己的 HTTP 适配、用例和 PostgreSQL 适配；不要把业务查询集中到全局 `internal/store`。
- `internal/` 领域包括 identity、catalog、inventory、leases、orders、messaging、billing、providers、compliance、realtime；`identity` 覆盖用户、会话与组织成员关系。边界明确，按切片逐步实现。领域包不依赖 HTTP 或具体数据库，`platform` 不反向依赖业务领域。

## 2. 身份与组织

- 覆盖注册登录、用户资料、组织成员和角色、API Key、会话撤销及后台操作审计。
- 浏览器会话优先使用安全 HttpOnly Cookie，正确实现 CSRF 防护、会话过期和速率限制。
- 每个接口执行租户级和对象级授权，不能信任前端提交的组织、资源归属或角色声明。
- 不将长期身份凭据交由前端存入 localStorage 或 Zustand。

## 3. 号码目录、库存与供应商

- 建模国家地区、号码类型、授权供应商目录、可用资源、定价快照、资源锁定、独占租约、号码生命周期和隔离策略。
- 真实库存、价格与可用性必须来自授权供应商接口，不能编造。
- 通过独立 Provider Adapter 隔离供应商接口，覆盖能力发现、资源与报价查询、申请释放号码、入站 Webhook 验签、消息归一化、幂等、补偿、超时和限流。
- 配置供应商合同及允许的业务范围，不假定所有供应商支持短租、退款或立即释放。
- 首先实现明确标识的 Mock Provider 用于端到端开发与测试。Live Provider 仅在具备明确商业授权与正式 API 文档时接入。

## 4. 订单与租约

- 订单和号码租约是不同领域实体，分别定义明确的状态机、合法转换与审计事件。
- 保证原子租约分配、并发下防止重复租约、订单幂等、可靠超时处理和上游失败补偿。
- PostgreSQL 是持久业务状态来源；Redis 仅用于缓存、限流和短期协调，禁止仅靠 Redis TTL 决定交易最终状态。
- 任务通过 River 可靠执行，明确重试、幂等及事务边界，不以进程内定时器替代关键任务可靠性。

## 5. 消息与实时事件

- Webhook 必须验证身份，原始事件可靠持久化，并以供应商事件 ID 去重；正确处理重复、乱序和重试。
- 入站消息匹配合法有效的租约，无法匹配或异常的消息进入隔离流程。
- 敏感消息加密保存，执行用户级和租户级访问隔离，提供留存、过期、删除与访问审计策略。
- 不得将短信验证码、完整消息内容或其他敏感凭据输出到日志、Tracing 或错误监控平台。
- SSE 提供实时变化事件与断线恢复，不替代数据库持久状态；定义可供前端按资源更新缓存的事件契约。

## 6. 计费与账本

- 覆盖充值订单、支付结果、余额、资金预留、扣款、退款、不可变账本、供应商费用、对账和异常交易。
- 金额使用 Decimal 或最小货币单位并明确币种，禁止浮点数计算金额。
- 账本记录不可变，纠错通过可审计的补偿记录完成；保证并发下不会重复扣款或结算。
- 支付 Webhook 验证真实性，资金结算保证幂等。支付机构须允许该业务模式并完成相应业务审批。

## 7. 合规与风险控制

- 实现用户与组织验证、用途声明、供应商授权记录、场景白名单、异常限流、消息访问审计、投诉处理、隐私留存策略、号码暂停和封禁。
- 不允许公共共享验证码收件箱、跨租户读取短信及根目录规范禁止的滥用功能。
- 安全、交易一致性和数据最小化是实现约束，不得因开发方便绕过。

## 8. API 契约

- OpenAPI 契约存放于 `backend/openapi/`，是接口的单一事实来源；由此生成 TypeScript Client，禁止手工重复维护前后端传输类型。
- 接口至少覆盖 `/v1/auth/*`、`/v1/me`、`/v1/organizations/*`、`/v1/catalog/*`、`/v1/numbers/*`、`/v1/leases/*`、`/v1/orders/*`、`/v1/messages/*`、`/v1/billing/*`、`/v1/api-keys/*`、`/v1/events/stream` 和 `/v1/admin/*`，按实施阶段逐步落地。
- 列表接口统一分页、排序、筛选；接口统一错误结构与 Request ID。
- 创建订单、租约、充值和退款支持 `Idempotency-Key`，核实重试时的业务副作用和返回结果一致性。
- 核心 API 由 Go 实现，前端不能成为权限或状态机的权威来源。

## 9. 工程质量与验证

- 建立真实错误处理、结构化日志、Tracing / Metrics、部署配置与可运行说明；不得输出敏感消息。
- 随功能建立 Go 单元测试、PostgreSQL 集成测试和契约测试。
- 重点验证 Webhook 重复和乱序、并发租约、钱包双重扣款、SSE 重连、跨租户访问隔离、网络超时与任务重试。
- 数据库变更提供迁移；SQL 和 sqlc 生成结果保持一致，不手工修改生成代码。
- 后端改动运行适当的格式、静态检查、测试与构建；依赖数据库或外部服务的检查必须真实执行，无法执行时明确说明。
- Mock 不能代替关键一致性、安全和持久化逻辑的验证，不以静态响应伪装真实服务。

## 10. 实施顺序

1. 基础项目、数据库、OpenAPI、用户身份，与前端协调设计系统和客户端契约。
2. 授权供应商 Mock、号码目录、独占租约与订单状态机。
3. 入站消息、Webhook、River、SSE 与消息收件箱所需 API。
4. 计费账本、充值、退款与对账。
5. 运营管理、安全审计与合规工作流。
6. 正式供应商接入、生产部署与性能验证。

接到业务实现任务时，先阅读现有实现和规范，核实关键依赖，明确本切片的模块边界、API、实施计划及完成标准，然后实现、测试并修复失败。不要把所有阶段一次性生成成未经验证的空壳；仅整理规范时不启动业务开发。
